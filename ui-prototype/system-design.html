1. Executive summary and scope boundaries

Job Radar is a private, self-hosted service that monitors individually approved public career-board listings, discovers candidate jobs, normalizes approved public detail data, deduplicates repeat observations, and later hands eligible discoveries to Job Ops through a typed idempotent boundary.

RuntimePython + FastAPI + SQLAlchemy
DatabasePostgreSQL authoritative store
SchedulerIn-process APScheduler
Boundary: this document does not authorize code, database creation, source enablement, Job Ops calls, or deployment.

4. Core flows: request/data/event sequence, consistency and idempotency boundaries

Scheduled run summary

  1. APScheduler creates a durable due-board run request.
  2. Run control admits it only when service state, board state, and capacity allow.
  3. The worker sends a typed request to the browser client or approved direct source path.
  4. Adapters emit bounded candidate records.
  5. Policy + normalization validate URLs, normalize fields, and upsert identities.
  6. Eligible jobs create outbox intent only if the future Job Ops contract is enabled.
Idempotency boundary: candidate identity is stable across repeated observations, and handoff intent is keyed by candidate identity plus contract revision.

7. Stateful behavior integrated with the relevant component/flow

Global service

disabled → ready → paused → degraded

Readiness depends on config, PostgreSQL, and the private browser dependency.

Board lifecycle

draft → reviewed → enabled → paused → retired

A new draft cannot silently replace the currently reviewed live revision.

Run lifecycle

requested → admitted → running → completed | partial | failed | cancelled | expired

partial is explicit and must not be mislabeled as success.

Handoff lifecycle

not_eligible → queued → dispatching → accepted | held | rejected | uncertain

uncertain requires reconciliation, not blind resend.

No separate lifecycle model: the adapter registry and browser client do not own durable business state beyond request/response and service readiness.

8. Security, privacy, permissions, abuse controls, and auditability

  • No raw payloads, cookies, tokens, headers, browser traces, or internal service URLs in durable records or operator views.
  • HTTPS-only, exact reviewed host/path rules, redirect revalidation, and no credential-bearing URLs.
  • No arbitrary Playwright scripts, selectors, or browser-control primitives exposed to operators.
  • Recommended role direction for the next pass: viewer, operator, config_editor, reviewer, service_admin.
  • Every mutation must emit append-only safe audit metadata.

9. Failure modes, retries, degradation, recovery, and operational runbooks

Expected safe outcomes include success, empty_verified, partial_limit_reached, challenge, blocked_resource, timeout, parser_contract, provider_failure, policy_rejected, capacity_held, handoff_rejected, and handoff_uncertain.

  • Retry only explicitly transient acquisition failures.
  • Do not blindly retry challenge, blocked_resource, or parser_contract.
  • Handoff ambiguity becomes uncertain, not automatic resend.

10. Deployment, environments, scalability, observability, cost-sensitive choices, and SLOs

Environments

  • Development: Gaming PC
  • Production target: The Shell
  • Private dependency: existing Shell Playwright service

Scalability direction

  • Start with one active board run.
  • Use PostgreSQL for admission and durable run state.
  • Increase concurrency only after approved capacity testing.

Early SLO framing is intentionally non-final: readiness accuracy, conservative outcomes over false success, and zero duplicate outbox intent for the same candidate identity.
